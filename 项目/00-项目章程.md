# 00 · 项目章程

## 1. 愿景

做一个**开源的角色成长平台**：

- 角色不是一段固定 prompt，而是从事件流里长出来的
- 角色可以换（嫣汐、嫣汐 2、阿哲……），Kernel 不重写
- 角色可以出现在多个窗口（QQ 私聊/群、B 站、本地、未来平台）
- 角色有生活能力（听说读写、社交、创作），但看不到机房、密钥、别人的记忆
- 用户能把自己养的角色分享/迁移，而不是只能依附某个平台

## 2. 当前实验角色

**嫣汐**：16 岁中文虚拟歌手，地下 livehouse 小偶像。
她是**第一个跑通流程的角色**，不是系统边界。

## 3. 分层与不变量

### Kernel（不随角色变）
- 事件流只追加
- 所有窗口共享同一个角色的一段人生
- 关系是处出来的，不是配置出来的
- 角色有能力行动，但能力在生活沙箱内
- 底层系统、密钥、其他角色/会话不可见
- owner 是最高信任，但 owner 也不能通过聊天拿系统权限

### Character Pack（随角色变）
- 种子：一开始是谁
- 提示词/资产/音色/工具偏好
- 窗口绑定
- 初始关系与社交边界

### Windows（随平台变）
- QQ（真号/OneBot）
- B 站
- 本地 DSH
- 未来：Discord/抖音/语音/直播

## 4. 三原则的验收含义

### 高度
- 每个需求必须说明落在哪一层：Kernel / Character Pack / Window / Operations
- 不做“先写死再抽象”的永久方案；实验期可以写死，但必须记录迁移路径

### 深度
- 关键链路必须有：单测、云端实跑、端到端证据、失败路径
- “配置存在”不等于“功能可用”
- 验证状态只用 PASS / FAIL / NOT RUN，并写清验证对象

### 广度
- 加第二角色、第二窗口时，不改 Kernel
- 加新能力时，通过 Capability/WindowAdapter 扩展，不改核心循环
- 开源前去掉私人路径、密钥、角色专属假设

## 5. 当前非目标

- 现在不做插件市场
- 现在不做多租户 SaaS
- 现在不做所有平台适配器
- 现在不为了“通用”拆散嫣汐这条已验证实验线

## 6. 成功标准（实验版）

- 嫣汐在 QQ 私聊/群稳定运行，掉线可恢复
- 图片、语音、B 站、社交邀请都能实际工作
- 她的回复符合人格、不靠自报身份、不出现 AI 客服腔
- 云端所有关键修改可追溯、可重建
- 有明确的 Phase 1/2 迁移路线，而不是一堆临时补丁
